# Agreement with references

The TypeScript model in `src/sim/` is compared, scenario by scenario, with external references. Each reference is a different kind of evidence, and each has its own section here with its own figure.

| Reference | Id | What it is | Evidence for |
|---|---|---|---|
| [BLIS](https://github.com/inference-sim/inference-sim) (inference-sim) | `blis` | A discrete-event simulator that runs the [llm-d](https://github.com/llm-d/llm-d) router's own code (its Endpoint Picker, in process) in front of a Go translation of [vLLM](https://github.com/vllm-project/vllm)'s scheduler | Decisions of llm-d and vLLM as simulated |
| [Measured vLLM](https://github.com/casys-kaist/LLMServingSim) | `vllm-measured` | Real vLLM runs of 300 ShareGPT requests on one RTX PRO 6000 and on one RTX 4090 (data published with LLMServingSim, MIT licence) | Real timings and KV block counts on two workstation GPUs, one workload |
| [LLMServingSim](https://github.com/casys-kaist/LLMServingSim) (MIT licence) | `llmservingsim` | A Python port of vLLM's V1 scheduler and block pool whose step times come from per-layer kernel tables profiled on real GPUs (here the RTX PRO 6000 and the RTX 4090) | A second, independent implementation of vLLM's scheduling and caching decisions, with profiled-kernel timings; its authors validated it against the measured runs above |

This page says what agreement shows, what it does not, how it is produced, and where the model and each reference differ. The machinery is in [`conformance/`](../conformance/README.md); the plan it followed is [`blis-conformance-plan.md`](blis-conformance-plan.md).

## How it is produced

- **Shared, neutral scenarios.** One YAML file per scenario in [`conformance/scenarios/`](../conformance/scenarios/) describes the deployment, the request list and the checks, with model and GPU names that neither the model nor any reference owns. Every tolerance and its one-line justification is written into the scenario before its first comparison run.
- **One adapter per reference.** `conformance/refs/<id>/` implements the `Reference` interface (`conformance/refs/reference.ts`): what it supports (models, GPUs, mechanisms, quantities), how a scenario becomes its native input, how that is run or loaded, and how the raw output is reduced to the one comparable record. A reference may be a simulator that is run or measured data that is reduced; either produces the committed file for a scenario. `conformance/translate/` holds the TypeScript model's own translation.
- **Pinned, committed references.** Each reference pins what it was made from in a lock file (BLIS: `conformance/refs/blis/lock`, a commit; there is no submodule, CI clones and builds it). Its output for each scenario is reduced and committed under `conformance/reference/<id>/`, with a hash of everything the reference was given. The ordinary test run needs no external tool; it fails if a scenario changed without its reference being regenerated.
- **Which references apply.** A check applies to every reference that supports the scenario's model, GPU and mechanisms and can state what the check compares, unless the check names its references. Each reference has its own `known_difference` records.
- **When two references cover a check.** They are first compared with each other by the check's own rule. If they agree, the model is held against each. If they disagree, the gap between them is recorded and explained in the scenario (`reference_gap`, asserted exactly), and the model is held against the span they leave: a check never passes merely by matching the more convenient reference. Cross-reference standings are in the last section.
- **CI jobs.** `conformance` (every pull request) runs the model on every scenario and compares it with the references. `blis-references` (nightly, and when the pin, a scenario or a translator changes; it regenerates only BLIS's references) rebuilds the pinned BLIS, regenerates the references and the fit, and fails if they differ from the committed ones. `blis-upstream` (weekly, allowed to fail) does the same against BLIS's `main`, to see drift before the pin is bumped. `llmservingsim-references` (nightly, and when its adapter changes) builds the pinned LLMServingSim on Ubuntu, reproduces its own committed result for the measured example, regenerates its records and fails if they differ.
- **The rule on differences.** A check holds as stated, or it carries a `known_difference` with a reason and the exact values that differ, and the test asserts the observed difference equals the recorded one: it fails if the difference disappears or changes. A failing check is fixed in the model only when the model is demonstrably wrong against the vLLM or llm-d source; otherwise it is recorded. A tolerance is never widened to make a test pass, and a scenario is never tuned until it agrees.

Three kinds of check: **exact** (integers and decisions that must be equal), **calibrated** (a timing or rate within a relative tolerance after the fit) and **directional** (the same intervention moves the same metric in the same direction by a similar factor).


## BLIS

### What agreement with BLIS shows, and what it does not

**It is evidence that the model makes the same decisions as llm-d and vLLM 0.32** for routing, flow control, engine scheduling (admission, chunked prefill, preemption) and KV accounting (block budget, prefix reuse), in the situations the scenarios construct. BLIS embeds the router's code and ports the scheduler with references to the vLLM source lines, so an exact check that passes is a check against those implementations as BLIS runs them.

**It is not a measurement on a live cluster.** BLIS is itself a simulator: its router sees scraped metrics that BLIS generates, its engines are modelled and not real GPUs, and its step costs come from fitted coefficients. The scenarios are small and constructed. Nothing here says that a deployment of llm-d and vLLM would produce these numbers.

**Timings are calibrated to BLIS, not measured.** The cost model is a roofline with two achieved-rate factors (MBU, MFU) and a host-time term. For each model and GPU these are fitted to BLIS's step times on calibration scenarios, and the fitted model is then checked on held-out scenarios. That shows the roofline can reproduce BLIS's timings within the stated tolerances where the checks hold, and records where it cannot. It says nothing about how close either is to hardware. The site's defaults for MBU, MFU and host time are not changed by the fit; the table below shows how far the fitted values are from them.

**Directional checks are weaker than exact ones.** Where the two simulators follow different rules by design (the autoscalers), or store different things (BLIS evicts KV chunks, the model whole sessions), only the direction and rough size of an intervention's effect is compared, within a factor band written beside the scenario before it was run.

### Decisions on tolerances

A tolerance may be set or changed only by a dated, recorded decision with a reason that does not depend on the observed result. The decisions so far:

- **2026-11-16, repository owner: KV blocks per replica are a capacity, checked within 0.1%, not for integer equality.** Both simulators derive the pool from estimates (the activation peak, the rounding of the weights), so equality of the integer is not the meaningful criterion. The tolerance is 0.1% because the terms that remain are estimates on both sides, and a difference below one part in a thousand changes no admission decision in any scenario. The old values, kept for the record: 27,928 against 27,926 blocks for Llama 3.1 8B on one H100 (0.007%) and 74,790 against 74,760 for Llama 70B on four H200s (0.04%); the term-by-term explanation of each stays in the scenario file as a note. *Verification of the claim:* the model's pool was changed by minus and plus 0.1%, 1%, and 30 blocks, and all 36 scenarios were run again. Every decision (placements, cached tokens, preemptions, request fates) is unchanged in every scenario. 35 scenarios are bit-for-bit identical; the one that is built to sit at the edge of its pool (`preemption-overflow`, 3,601 blocks) keeps its one preemption and both completions and changes only times. Nothing else was relaxed: the round-robin, burst time-to-first-token and throughput, host-tier hit-rate and autoscaling-wait differences stay recorded.
- **2026-11-16, cost-model change (ADR 0008): bounds of the fit and no change of any tolerance.** The fit's bounds were set before the refit, from evidence that does not depend on it: MBU in [0.4, 0.95] (the two measured runs stream at 0.83 and 0.85 with every overhead included; BLIS's calibrated cost is at least 0.52), MFU in [0.2, 0.9] (measured prefill 0.62 of the peak), the all-reduce efficiency in [0.05, 1] and its fixed time in [0.5, 50] microseconds, host time as before. No tolerance of any check was changed by that change; the checks it moved from holding to differing (the two KV pools against BLIS, the overflow scenario's preemption count) and from differing to holding (every RTX PRO 6000 default check, most RTX 4090 ones, the burst throughput) are recorded in the scenario files with their numbers.

### Known differences

Each is a check that does not hold as stated. The values are the TypeScript model's, then BLIS's; the scenario file carries the same reason next to the check.

<!-- generated:parity-known-blis:start -->
- **`autoscale-overload` / `wait-falls`** (directional). Mean time to first token, which here is queue wait, is lower with the autoscaler. TypeScript / BLIS: effect: 0.08448 / 0.4021. Both fall, by different amounts, because the two autoscalers react at different times and reach different sizes. The TypeScript rule is concurrency based and acts on the count of requests in flight: it adds a replica at 1.1 s, 2.1 s and 3.1 s (one per second, as the count crosses 8, 16 and 24), so with the 5 s load time the new replicas serve from 6.1, 7.1 and 8.1 s, four replicas in all. BLIS's saturation analyzer (the llm-d workload-variant autoscaler's token-based rule) compares the tokens in the queue and in KV memory with 80 percent of the pool, so it waits until the queue holds enough prompt tokens: its first added replica serves from 11 s, its second from 18 s, and it stops at three. The queue therefore drains later and less in BLIS, and mean time to first token falls to 0.40 of the fixed arm's (8.3 s against 20.7 s) where the TypeScript model's falls to 0.084 (1.8 s against 21.0 s). The rules differ by design; the direction is the same.

- **`kv-budget-70b-h200-tp4` / `kv-blocks-per-replica`** (capacity). One tensor-parallel replica holds the same number of KV blocks as the reference, to within 0.1 percent. TypeScript / BLIS: value: 75768 / 74760. Same cause as kv-budget-8b-h100, on four GPUs: both use the same driver-reported memory (150,109,880,320 bytes), the same weights (141.1 GB split four ways) and block (5,242,880 bytes), and differ in the activation peak and the graph estimate by 1.318 GB per GPU (1,008 blocks across the pod, +1.3 percent). BLIS: 5 hidden-state rows per token of an 8,192-token step (671.1 MB) and a flat 1.160 GB for graphs. TypeScript model: a forward pass over 8,192 tokens with the feed-forward width split four ways (503.3 MB) and 9.9 MB of graphs for the 6 captured sizes of a 12-sequence engine (src/sim/cost/memory.ts). This check was within 0.04 percent (74,790 against 74,760) before the derivation was changed. Not tuned.

- **`kv-budget-8b-h100` / `kv-blocks-per-replica`** (capacity). One replica holds the same number of KV blocks as the reference, to within 0.1 percent. TypeScript / BLIS: value: 28539 / 27926. Both size the pool as vLLM does: ceil(driver-reported memory x utilisation) less weights, an activation peak and a CUDA-graph estimate; they agree on the memory (85,029,158,912 bytes), the weights (16.06 GB) and the block (2,097,152 bytes), and differ in the last two terms, by 1.284 GB (613 blocks, +2.2 percent). BLIS charges 11 bf16 hidden-state rows per token of a full 8,192-token step (738.2 MB, from NVIDIA's memory model through its registry) and a flat 1.160 GB for graphs (the median of 22 vLLM start-up logs). The TypeScript model derives both from the engine's settings the way vLLM's profiling does (src/sim/cost/memory.ts): the larger of a forward pass over 8,192 tokens (604.0 MB) and the sampler's 12 rows (small here), and, for graphs, a pool the size of a pass over the largest captured batch plus vLLM's floor of 1 MiB per further graph, 10.2 MB for the 6 captured sizes of a 12-sequence engine. The difference is almost all graphs: a flat median that does not depend on the settings against a figure that follows the capture list. Two measured vLLM runs (RTX PRO 6000, RTX 4090) set aside 0.90 and 1.24 GB for everything but weights and KV, against 0.25 and 0.47 GB for the model's derivation and 1.9 GB for BLIS's, so neither is exact; the model's is closer on both. This check was within 0.007 percent (27,928 against 27,926) before the derivation was changed; that agreement was between two estimates that both overshoot the real overhead. Not tuned.

- **`preemption-overflow` / `preemption-count`** (exact). Exactly one preemption happens, and both requests finish. TypeScript / BLIS: value: 0 / 1. This scenario is built so that two growing sequences outgrow the pool: each needs 32,000 tokens, 2,000 blocks, so together 4,000 blocks, and the pool was made smaller than that (30 percent memory utilisation). BLIS's pool is 3,601 blocks (57,616 tokens), so the second sequence is preempted once. The TypeScript model's pool is now 4,212 blocks (67,392 tokens), 611 blocks more (+17 percent; the same memory terms as kv-budget-8b-h100, a pool 2.2 percent larger at full size, but here the pool is a quarter of the memory, so the same 1.3 GB weighs 17 percent), which is more than the 4,000 the two need, so both finish without a preemption. The mechanism is unchanged: the model's preemption, recompute and re-admission are exercised by the on-demand overload preset and by the unit tests in src/sim/admission, whose sequences are drawn from a distribution and do overflow the pool, and the decisions of this scenario that do not depend on the pool (both complete) still agree. The scenario was written to the pools of 2026-11-16 ("the two pools agree to a few blocks") and is left as it was: moving its memory utilisation to restore the preemption would be choosing a parameter after seeing the result. Not tuned.

- **`routing-round-robin` / `pod-sequence`** (exact). Request i goes to the replica after the one request i-1 went to, wrapping after four (replicas are named by first use, since which replica starts is arbitrary). TypeScript / BLIS: 8 values differ, for example s2/r0: 1 / 0; s3/r0: 2 / 1; s4/r0: 3 / 0. The TypeScript model rotates strictly through the replicas (Envoy's round robin), so request i goes to replica i mod 4. The llm-d router has no such policy. The closest configuration, which BLIS ships as reference-configs/round-robin.yaml and runs here, is the max-score picker with no scorers: every replica ties and the picker rotates the tied candidates by a counter, but the scheduler first puts the candidates in a seeded random order before every pick (scheduler_profile.go:363-370 in the router fork, added by the fork's hosting change; outside hosting the order is Go map order, which is not fixed either), so the choice is uniformly random among the tied replicas, not a cycle. The fork's reference-configs README says so: "it does not rotate". BLIS's draw for this trace is deterministic for the pinned build and seed. There is no llm-d behaviour for the TypeScript policy to be consistent with; it models Envoy, not llm-d.

- **`routing-round-robin` / `requests-per-pod`** (exact). Twelve requests over four replicas is three each. TypeScript / BLIS: rank0: 3 / 4; rank1: 3 / 4; rank3: 3 / 1. Same cause as pod-sequence. A strict rotation gives 3, 3, 3, 3; llm-d's random choice among tied replicas gave 4, 4, 3, 1 for this trace (counts sorted from the busiest replica; deterministic for the pinned build and seed). The llm-d configuration is balanced only on average.

- **`tiers-offload` / `host-tier-hit-rate`** (directional). With the tier, a share of prompt tokens is served from host memory; without it, none is. TypeScript / BLIS: effect: 0.4984 / 0. BLIS reports a host-tier hit rate of zero in this run (`cpu_tier_hit_rate` in its Result; the per-request rows carry no external-token count either) although the run shows the tier working: a follow-up's scheduling delay is 56.6 ms with the tier against 41.1 ms without (the 15.5 ms is the copy of about 3,050 tokens of KV, 400 MB at about 26 GB/s), and the step that prefills it takes 12.6 ms against 63.1 ms, because the history is no longer recomputed. The TypeScript model reports that 49.8 percent of all prompt tokens came from host memory. I did not find why BLIS leaves the counter at zero for a reload that completes before the request is first scheduled (its lookup is recorded at first admission, and a request whose load has landed is scheduled without a new prefix lookup, blis-vllm batch_formation.go); the timing check below shows the effect on time to first token, which both report.

- **`timing-8b-h100-burst` / `ttft-mean`** (calibrated). Mean time to first token agrees with BLIS after calibration. TypeScript / BLIS: value: 0.7282 / 0.5452. The prefill cost curve is the main cause; the arrival handling is a minor one. A full 8,192-token prefill step takes about 139 ms in BLIS (steps between the groups of prompts it batches: 362 ms less 223 ms) and about 217 ms in the TypeScript model (214.4 ms of GPU time at the fitted MFU of 0.714 and 3.0 ms of host time): the fitted MFU is a compromise between BLIS's short prompts, where the fit leaves the model faster than BLIS, and its long ones, where it is slower (on the calibration scenarios the fitted time to first token is -13 to -16 percent on the batched short-prompt ones and +18 and +20 percent on calib-8b-h100-isolated and batch16-long, whose prompts are long), because a single efficiency factor cannot bend like BLIS's size-dependent prefill cost. A burst is a queue of full prefill steps, so it sits on the steep end. The minor cause: BLIS passes each request through an admission queue (a tokeniser pool with a per-token service time and a fixed delay, docs/guide/latency-models.md in inference-sim), so requests that arrive together reach its engine one after another (its first request is prefilled alone and sees its first token after 75 ms), where the TypeScript model's front end tokenises all 32 at once and its first step already carries 5 prompts. Measured on 2026-11-16 by running the same trace through the pinned BLIS with `--renderer-num-workers 0`, which removes that serialisation, BLIS's mean time to first token moves only from 545 to 529 ms (and its first request's from 75 to 179 ms, because the whole admission time becomes an uncontended delay for every request), so the serialisation explains about 3 percent of BLIS's own value and little of the gap. The result is 34 percent more mean time to first token (39 percent before the step cost was changed to MBU 0.85, an explicit launch time per layer and a refit). Decoding agrees (time per token +1.1 percent, end to end +6.3 percent, throughput -5.8 percent, all inside tolerance).

Changes made to the model because the first comparison showed it wrong against the vLLM source (not recorded as differences): a finished request caches `prompt + output - 1` tokens, and a waiting request is admitted only when its whole input sequence fits in the free blocks. Both are in the model's history, with their sources in `src/sim/engine/`.

## Measured vLLM

Real vLLM runs on real GPUs, not a simulator. The measurements are the ones [LLMServingSim](https://github.com/casys-kaist/LLMServingSim) (MIT licence, CASYS Lab at KAIST) publishes under `bench/examples/<GPU>/<model>/vllm/`; nothing of its simulator is used. Two examples are used, the ones the model can represent: Llama 3.1 8B on one RTX PRO 6000 Blackwell Server Edition (vLLM 0.31.0) and on one RTX 4090 (vLLM 0.19.0).

### What was measured, and its limits

- **The workload.** 300 ShareGPT requests (257,239 prompt tokens, 195,753 output tokens, the same list on both GPUs), sent by a client at about 10 requests per second over 29 s. Each record gives the client's send time, the prompt and output token counts, and the engine's first-token and last-token times. The load exceeds what either card serves (about 6,750 output tokens per second asked for; 3,068 served on the RTX PRO 6000, 1,066 on the RTX 4090), so a queue builds and the later requests wait for most of the time to first token. One workload, one model, one engine per GPU: this is evidence for how far the model is from hardware under heavy load on these two workstation cards, and for nothing about other loads, other models, other GPUs, routing or multiple replicas.
- **What the times mean.** Time to first token is the first-token time minus the send time, with the engine's monotonic clock moved to the client's epoch clock by one offset (the smallest `queued_ts - arrival_time` of the run, as the data's own validator estimates it). That includes the wait before the engine picked the request up (at most 95 ms on the RTX PRO 6000, 201 ms on the RTX 4090). Time per output token is `(last - first) / (output tokens - 1)` per request; the model's values are computed the same way from its rows (`record.ts`).
- **Engine settings.** Taken from the runs' `meta.json` and copied into the scenario: `max_num_seqs` 128 and 256, `max_num_batched_tokens` 2048, chunked prefill, prefix caching on, `gpu_memory_utilization` 0.92 and 0.9, block size 16. The reference refuses a scenario whose requests or settings differ from the run in any way, so a scenario cannot be tuned away from the measurement.
- **Prefix caching and token ids.** The real engine served 19,552 of the 257,239 prompt tokens (7.6 percent) from its prefix cache on the RTX PRO 6000 (the RTX 4090 run did not record it): ShareGPT prompts share leading text. The model's trace has no token ids, so it sees no reuse. This makes the model do more prefill work than the engine did, by about that share of prompt tokens.
- **Represented since 2026-11-16 (ADR 0008):** asynchronous scheduling (the scenarios set it, host time then overlaps GPU time) and CUDA-graph replay (a per-layer launch time, lower up to the largest captured step). **Not represented:** the API server's tokeniser pool, `max_model_len`, vLLM's prefix-cache reuse after a preemption, and the vLLM version differences (0.31.0 against 0.19.0; 0.19.0 does not subtract a graph estimate from the pool). The RTX 4090 run did not record preemptions or prefix hits.
- **Licence.** LLMServingSim is MIT-licensed. Only a reduction is committed (`conformance/refs/vllm-measured/data/`): per request the arrival, token counts and first/last token times, the engine settings and KV block count, and totals of the per-second statistics, with the repository, the commit (`conformance/refs/vllm-measured/lock`), the SHA-256 of each source file and the copyright holder. The licence text is kept beside it (`LICENSE-LLMServingSim`). `pnpm conformance:extract` (with `LLMSERVINGSIM_DIR` naming a clone at that commit) regenerates the data; `pnpm conformance:reference --ref vllm-measured` turns it into the records the tests read.
- **GPUs.** Added to the hardware catalogue for these scenarios: RTX PRO 6000 (96 GB GDDR7, 1,597 GB/s; NVIDIA's page gives "1 PFLOP" for FP16/BF16 tensor cores without saying so; it is the sparse figure: table 4 of NVIDIA's RTX Blackwell GPU architecture whitepaper gives 503.8 TFLOP/s dense, BF16 with FP32 accumulate, and 1007.6 with sparsity, so the model uses 503.8) and RTX 4090 (24 GB GDDR6X, 1,008 GB/s, BF16 tensor with FP32 accumulate 165.2 TFLOP/s dense, from NVIDIA's Ada whitepaper). The memory a driver reports comes from the runs themselves (`device_total_memory_bytes`: 101,976,440,832 and 25,250,627,584 bytes), which is what sizes the KV pool.

### Two readings of timing

They are different questions and are never pooled.

1. **Default parameters, no fit** (`default-*` checks, all 300 requests): how far the model is from real hardware out of the box, with the site's MBU 0.85, MFU 0.7 and host time of 1.5 ms plus 0.05 ms per sequence (until 2026-11-16: MBU 0.6, MFU 0.5; see ADR 0008), the engine's own settings including asynchronous scheduling, and everything else the model's.
2. **Fitted, held out** (`fitted-*` checks, the last 200 requests): MBU, MFU and the two host-time terms are fitted to the first 100 requests by arrival, and the checks are computed on the other 200. What was fitted to what: the model's per-request time to first token for the first 100 requests and their mean time per output token, from the same run's measurements, by the same coordinate search used for BLIS (`conformance/calibration/fit.ts`); nothing is fitted to the held-out requests, and nothing else in the model was changed. This is a weak held-out test, since the 200 later requests are from the same run, the same card and the same workload, and the engine is saturated for them but not for the first 100 (mean time to first token 0.14 s for the first 100, 6.2 s and 13.2 s for the next two hundreds), so the fit sees almost no queue and the check is on queue waits.
3. **Fitted on the other card** (`crossfit-*` checks, all 300 requests): MBU, MFU and host time fitted to the first 100 requests of the run on the other GPU, then the model run for this GPU (its own datasheet, memory and engine settings) over every request. Nothing about this card or this run is in the parameters, so it is held out without a split. It is the stronger test, and it is not passed in both directions: see the known differences.

The tolerances (30 percent for time to first token, 12 percent for time per token, 15 percent for end to end, 10 percent for throughput, and 20 percent at the 99th percentile of time per token and end to end) were written into the scenario before the first comparison; they are the ones the BLIS timing checks use. The KV capacity check applies the 0.1 percent rule of 2026-11-16 unchanged to a real engine.

### What this says for the cost model

The cost model was changed on 2026-11-16 as a result of this reference (ADR 0008). (1) The structure of the decode step was right and the default was wrong: from the runs' per-second statistics a decode step streams its weights and KV cache at 0.83 (RTX 4090) and 0.85 (RTX PRO 6000) of the datasheet bandwidth, so the default MBU is now 0.85 (it was 0.6), and the model's step for the 4090's saturated batch is 26 ms against the run's 24.4 to 25.9. (2) Host time overlaps the GPU in an engine that schedules asynchronously, as both did. (3) The activation term was sized for an 8,192-token step and 256 sampler rows whatever the settings; it is now derived from `max_num_batched_tokens` and `max_num_seqs` as vLLM's profiling pass does, which with a flat graph term had made the pool 1.3 percent short and 12.1 percent short; it is now 0.8 percent and 14.1 percent over, the rest being memory the engine's profile counted outside torch's allocator and the real size of its CUDA graphs, which no closed form here derives. (4) What remains of the RTX 4090's error is not the cost of a step but a mechanism: the model recomputes a preempted request from zero (169,000 tokens, 66 percent of the prompt tokens) where vLLM's prefix cache would keep what was not yet reused. (5) The tensor-parallel and per-layer terms cannot be tested with this data, which is single-GPU; BLIS is their reference.

## LLMServingSim

[LLMServingSim](https://github.com/casys-kaist/LLMServingSim) (CASYS Lab at KAIST, MIT licence), pinned at the commit in `conformance/refs/llmservingsim/lock`, run as a simulator from a checkout. It is a Python port of vLLM's V1 scheduler (running requests first, tail preemption with recompute, no admission in a step that preempted, chunked prefill, `max_num_seqs`, `max_num_batched_tokens`) and block pool (chained block hashes over real token ids, so prefix caching needs ids), with CPU and CXL KV tiers, prefill/decode instances priced by ASTRA-Sim, speculative decoding by acceptance rate and routing by `RR`, `RAND` or `LOAD`. Step latency is the sum of per-layer kernel times profiled on real GPUs: here an RTX PRO 6000 and an RTX 4090, Llama 3.1 8B. It has no llm-d scorers, no flow control or shedding and no autoscaling, so none of the checks on those are covered.

### What agreement with LLMServingSim shows, and what it does not

- **Shows:** that the model makes the same admission, preemption, prefix-cache and placement decisions as a second, independent port of vLLM's scheduler, in constructed situations, and how far its timings are from a simulator whose step times come from kernels profiled on the GPU in question and which its authors validated against the real vLLM runs of the measured section at about 1 to 5 percent.
- **Does not show:** that either is right about real hardware (it is a simulator; the measured section is the evidence for that); anything about llm-d or routing beyond round robin; anything on the GPUs it has no profile for (no H100, H200, B200, MI300X).
- **Not independent of the measured runs.** Its authors validate it against exactly the 300-request runs of the measured section, and on the RTX 4090 they set its memory utilisation to reproduce the real engine's KV block count. Where it agrees with the measurement on those scenarios, that is its validation, not a second opinion on the model; the check that matters there is whether the model is inside what both say.
- **KV capacity is arithmetic.** It computes `(memory x utilisation - weights) / bytes per block` and says it does not model the activation peak or CUDA context, so its block count is an upper bound derived from its input. On the RTX 4090 the utilisation is the authors' calibration to the measured block count, so the capacity check is not asked of it there (`references: [vllm-measured]`). On the RTX PRO 6000 it is compared as what it is: the model's accounting against weights-only arithmetic.
- **What is scraped, what is patched.** Nothing is patched. At the default log level the run prints its KV capacity per instance, its preemption count (only when not zero), total requested and prefix-hit tokens (NPU and CPU) and, every simulated second, the cumulative hit counters; it writes a per-request CSV (arrival, end, queuing delay, time to first token, tokens). A request's cached tokens are the increase of its instance's counter in the second it was admitted; the adapter returns them only when each second holds at most one admission that hit the cache, and checks that they add up to the printed total. That was verified against an instrumented run (a temporary print in its scheduler, not kept) on `lss-prefix-cache`: all eight follow-up values equal, and the run's CSV byte-identical with and without the print. With a host tier or a prefill/decode split the per-request value is not reported.
- **Token ids.** The scenarios carry token counts. The translator gives every token a fresh id and builds a follow-up's prompt as previous prompt, previous output, new tokens, so sharing is exactly what the conversation implies. For the 300 ShareGPT requests the sharing is the real one: the committed data (`conformance/refs/llmservingsim/data/`, a reduction of the example's workload with the cluster configuration, the SHA-256 of each source file and the licence text) records, for each request, the earlier request sharing the longest prefix and its length, and the translator rebuilds ids with that prefix trie. Its prefix cache then serves 19,520 of the 257,239 prompt tokens (7.59 percent) where the real engine served 19,552 (7.60 percent).
- **Reproduction first.** At the pinned commit its committed result for the RTX PRO 6000 example (`bench/examples/RTXPRO6000/Llama-3.1-8B/outputs/sim.csv`) is reproduced byte for byte on macOS arm64 (the committed file was made on Linux), and the nightly job checks it on Ubuntu before regenerating anything. Through the scenario (arrivals are the client's send times, not the dataset's nominal ones, a few milliseconds apart) the results are within 1 percent of its own.
- **Features left out.** Prefill/decode transfer times are not reported (so the link rate cannot be fitted to it), and its time to first token ends at the prefill instance. Its speculative decoding is listed upstream as not yet validated against measured runs (open issue 85); here it behaves as documented (tokens per step 1 + rate x K) and is compared as an effect, not an absolute time. Open issue 47 (a decode instance can abort when it cannot hold a handed-over request) does not arise in the scenario, whose pools are far from full.
- **Licence.** Only reductions are committed, with the repository, the commit, the SHA-256 of each source file and the copyright holder; the licence text is kept beside them (`conformance/refs/llmservingsim/LICENSE-LLMServingSim`). `pnpm conformance:extract-llmservingsim` regenerates the data from a clone.

- **`lss-kv-budget-8b-rtx-pro-6000` / `kv-blocks-per-replica`** (capacity). One replica holds the same number of KV blocks as LLMServingSim derives from the same memory utilisation, to within 0.1 percent. TypeScript / LLMServingSim: value: 36174 / 37090. LLMServingSim sizes the pool as (memory x utilisation - weights) / bytes per block, with 94.97 GiB x 0.92 and 16.06 GB of weights, and gets 37,090 blocks; it states that it does not model vLLM's activation peak or CUDA context. The TypeScript model sets aside 735,313,920 bytes of activations (the peak of an 8,192-token step) and 1,159,725,056 bytes for CUDA graphs on top of the weights and gets 36,174 blocks, 916 (2.5 percent) fewer, which is 1.895 GB at 2,097,152 bytes per block. The real engine set aside about 0.900 GB for the same things (measured-8b-rtx-pro-6000), so the real figure lies between the two, nearer LLMServingSim's. This is arithmetic on both sides' inputs, not evidence about vLLM's start-up sizing.

- **`lss-pd-disaggregation` / `ttft-rises`** (directional). Splitting prefill from decode raises the mean time to first token (the hand-over and a second queue). TypeScript / LLMServingSim: effect: 1.279 / 0.8865. The effect has the opposite direction. The model's split arm has a mean time to first token of 217 ms against 169 ms colocated (x1.28): its first token is delivered after the KV cache has crossed to a decode replica, so it includes the hand-over and the wait for a decode slot. LLMServingSim's is 129 ms against 146 ms (x0.89): its time to first token is "the time when the computation of the first token is completed" (a comment in its main loop), on the prefill replica, so it excludes the hand-over, and the dedicated prefill replica is not delayed by decode steps, which makes it lower than colocated. The two define the first token differently; the hand-over itself is not reported by LLMServingSim, so the link cannot be fitted to it either. Neither is wrong, and neither is measured here: vLLM's disaggregated deployments differ in which instance returns the first token.

## Between references

For the first time two references cover the same checks: the two measured scenarios (`measured-8b-rtx-pro-6000`, `measured-8b-rtx-4090`: the same 300 ShareGPT requests) are answered by the real vLLM runs and by LLMServingSim, which its authors validate against exactly those runs. The suite compares the two references with each other first (`conformance/compare.ts`), then holds the model against each, and against their span where they disagree.

- **The references agree with each other.** On the 21 timing and rate checks of the RTX PRO 6000 and the 20 of the RTX 4090, LLMServingSim is within 1.2 percent of the measurement (median 0.3 percent), and its prefix-cache hits are 19,520 tokens against 19,552 (7.59 against 7.60 percent). This reproduces the authors' own validation through this suite's translation (client send times, token counts, engine settings); it also means that on these two runs LLMServingSim adds almost no information beyond the measurement, and its figures on the same scenarios are not a separate confirmation of what the model does.
- **The model is outside both, equally.** Of the 43 checks both cover, 20 hold against both (all of them the fitted, held-out readings, and the preemption count), 22 hold against neither (every default-parameter timing check, the prefix-hit rate on the RTX PRO 6000, and the RTX 4090's fitted 99th-percentile time per token), and the references disagree with each other on one. So where the model misses the measurement it misses LLMServingSim by the same amount: the default decode step is 50 to 60 percent slower than the profiled kernels and the real engine alike.
- **The one gap is the KV pool** (`measured-8b-rtx-pro-6000` / `kv-blocks-per-replica`): 36,649 blocks measured, 37,090 in LLMServingSim (1.2 percent more, because it sets nothing aside for activations or CUDA graphs and says so), 36,174 in the model (475 below the measurement, 916 below LLMServingSim). The model is outside their span by 1.3 percent, which is a known difference against the span, recorded with the term-by-term reason. On the RTX 4090 the two agree by construction (its authors set the memory utilisation to the real block count), so the capacity check there is asked of the measurement only.
- **What the second reference adds to the measured scenarios** is a second preemption count where the measurement has none (RTX 4090: the model 184, LLMServingSim 191) and a prefix-hit rate on the RTX 4090 (LLMServingSim 1.9 percent, the model none), which the real run did not record.

## What is not verifiable

These approaches have no check, and are not counted as agreement in either direction:

<!-- generated:parity-notverifiable:start -->
- **`admission/prompt`.** vLLM allocates KV memory as tokens are written and BLIS translates vLLM, so neither has a policy that reserves a whole prompt before admitting it; there is no counterpart to compare.
- **`admission/reserve`.** vLLM does not reserve KV memory for a request's whole output at admission, and BLIS follows vLLM, so there is no counterpart to compare.
- **`batching/static`.** vLLM does no static batching (it schedules continuously) and BLIS translates vLLM, so there is no counterpart to compare.
- **`kvcache/adaptive`.** BLIS reloads whenever its host-memory tier holds the prefix; it has no decision between copying and recomputing to compare. The scenario that exercises the tier (tiers-offload) is a check of the tiers, not of this rule.
- **`workload/closed-loop-sessions`.** BLIS replays traces and generates open-loop streams; it has no counterpart to the closed-loop sessions (users who wait, think and return) that the site generates, so the scenarios feed both simulators a trace instead.
- **`workload/trace-replay`.** It is how both simulators are given the same requests, not a mechanism BLIS models: every scenario uses it, and the conformance machinery fails when the two row sets differ, but there is nothing in BLIS to compare it with.
<!-- generated:parity-notverifiable:end -->

Also not covered, because BLIS or this suite does not compare it: AMD MI300X (not in BLIS's catalogue, so the model's MI300X entry has no counterpart); the SSD and shared-pool KV tiers (only the host-memory tier is compared); the router's scraped-metric delay (the model's router sees exact pod state; scenarios keep routing decisions unambiguous so this does not matter); and anything the site does that is not a mechanism, such as the animation.
