# ADR 0009: Three references, each evidence for something different

## Status

Accepted (2026-11-16). Builds on [ADR 0006](0006-modular-simulation-with-citations.md) and [ADR 0007](0007-calibrated-replay-mode.md); the `Reference` interface it uses is `conformance/refs/reference.ts`.

## Context

The conformance suite began with one reference, [BLIS](https://github.com/inference-sim/inference-sim), and gained a second, real vLLM timings published with [LLMServingSim](https://github.com/casys-kaist/LLMServingSim). A third was proposed: LLMServingSim itself, run as a simulator. The question is what it adds that the first two do not, and what to do when references disagree.

Facts about LLMServingSim at the pinned commit (`conformance/refs/llmservingsim/lock`): a Python port of vLLM's V1 scheduler and block pool (chained block hashes over token ids, tail preemption with recompute, chunked prefill, optional CPU and CXL KV tiers, prefill/decode instances priced by ASTRA-Sim, speculative decoding by acceptance rate, routing `RR`, `RAND`, `LOAD`); step latency from per-layer kernel tables profiled on real GPUs (an RTX PRO 6000 and an RTX 4090 for Llama 3.1 8B); no llm-d router, no shedding, no autoscaling; its KV capacity is arithmetic on the configured memory utilisation, with no activation estimate; its authors validate it against the measured runs at about 1 to 5 percent; the repository is very active, with essentially one maintainer and an announced port to another language.

## Decision

- **Three references, kept separate, each with its own section and figure.**
  - **BLIS** is evidence for *decisions of llm-d and vLLM as simulated*: the router's own code and a Go port of vLLM 0.32's scheduler. It covers routing, shedding, autoscaling, other GPUs and models, and nothing measured.
  - **Measured vLLM** is evidence for *what hardware did*: real timings and KV block counts of one workload on two workstation GPUs. It is the only reference that is not a simulator, and it covers no mechanism beyond one engine and one request list.
  - **LLMServingSim** is evidence for *a second, independent implementation of vLLM's scheduling and caching decisions, with profiled-kernel timings on two GPUs*, for the mechanisms BLIS covers differently or not at all (a host KV tier, prefill/decode instances, speculative decoding, `max_num_seqs`, preemption) and for timings on GPUs BLIS lacks. It is a simulator, not a measurement.
- **Agreement is never pooled across references.** A reference's headline figure counts only the checks it covers. A check on which two references disagree with each other is in neither figure; it is in the cross-reference section.
- **When two references cover a check** (`conformance/compare.ts`): they are compared with each other first, by the check's own rule. If they agree, the model is held against each and a miss is a known difference per reference. If they disagree, the gap is recorded and explained in the scenario (`reference_gap`, asserted exactly) and the model is held against the span they leave (a known difference with `reference: span`). A check never passes by matching the more convenient reference.
- **Independence is stated, not assumed.** LLMServingSim is validated by its authors against exactly the two measured runs, and its RTX 4090 configuration sets the memory utilisation to the measured block count. Agreement between it and the measurement on those scenarios (within 1.2 percent on all 41 timing and rate checks, a median of 0.3 percent) is its validation reproduced through this suite, not two independent witnesses for the model. So (a) the capacity check on the RTX 4090 is not asked of LLMServingSim (`references: [vllm-measured]`), (b) on the RTX PRO 6000 its capacity is compared as what it is (arithmetic without activations) and the gap with the measurement is recorded, and (c) the parity page says that on the measured scenarios it adds a second preemption count and a prefix-hit rate where the measurement has none, and little else.
- **A scenario may name its references** (`references:` at the top of a scenario). The measured scenarios replay one real workload and name `vllm-measured` and `llmservingsim`; scenarios built for LLMServingSim's inputs name it alone. Otherwise a reference answers every scenario whose model, GPU, mechanisms and arms it supports.
- **No patch.** Everything the adapter needs is read from LLMServingSim's CSV and stdout at its default log level. A request's cached prefix tokens are not reported; the adapter derives them from the cumulative hit counter in the second the request was admitted, only where that is unambiguous, checks the sum against the printed total, and otherwise reports none. The method was verified once against an instrumented run (a print in the scheduler, not kept) whose result file was byte-identical to the unpatched run's.
- **Pinned, and loud.** The adapter is pinned to one commit, reads lines and columns by name, and throws on any it cannot find. A nightly job (`llmservingsim-references`) builds the pinned commit, reproduces the upstream example's committed CSV, regenerates the records and fails on a difference; ordinary CI reads the committed records and needs only Node. Bumping the pin is a deliberate act (`conformance/README.md`).
- **Licence.** LLMServingSim is MIT-licensed. Nothing of it is vendored. What is committed is derived: the prefix structure of the example workload (for each request, the earlier request sharing the longest prefix and its length, not the token ids or text), its example cluster configurations, and the SHA-256 of every source file, with the licence text beside them.

## Consequences

- A disagreement between the model and one reference is no longer the end of the investigation: the others say whether it is the model's, the simulator's or the situation's. For the first time the suite has checks covered by two references; on the 300-request ShareGPT run the model's default-parameter timings are 50 to 60 percent off the decode step of both the real engine and the profiled kernels alike, and its KV pool is 475 blocks short of the measured one (and 916 short of LLMServingSim's).
- Disagreement between references is a finding about the references, recorded with its reason in the scenario file.
- More references mean more regeneration work after a change to the cost model: the default-parameter timing differences against LLMServingSim and the measured runs must be re-recorded. `pnpm conformance:report` prints the values; `pnpm conformance:calibrate && pnpm conformance:summary && pnpm docs:sync` regenerate the rest.
- LLMServingSim's repository changes fast. Pinning contains it, and the adapter's refusal to guess keeps a changed format from being read as a changed result. If its maintainers move to the announced port, the pin stays on the Python commit and this reference ages by design.
