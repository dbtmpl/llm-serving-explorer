# Glossary

- **Concept:** A decision a serving stack has to make, such as how to route or what to evict. Each has a module under `src/sim/`.
- **Approach:** One published or deployed way of making that decision. Implemented in its own file, with its sources.
- **Session:** One user conversation. It sends a first request and may send follow-up turns, go idle or leave.
- **Gateway:** The front end that assembles the prompt (history plus the new message) and turns it into tokens.
- **Router:** The component that picks a pod for each request. Modelled on llm-d's endpoint picker (EPP), which scores pods on prefix-cache affinity, queue depth and KV utilisation.
- **Pod:** One running copy of the inference engine with its GPUs. Pods are created, load weights, become ready, drain and terminate.
- **Sequence:** One request as the engine sees it while it runs: the prompt plus the answer generated so far. vLLM's name.
- **Batch slot:** One of the `max_num_seqs` places in a pod's running batch, drawn as a bar. A request holds one from admission until its last token.
- **Ridge:** The arithmetic intensity at which a GPU's peak FLOP/s and memory bandwidth limits meet (peak FLOP/s ÷ bandwidth). Left of it a step is memory-bound, right of it compute-bound.
- **Engine step:** One forward pass over the current batch. Every running sequence advances by one decode token or one prefill chunk.
- **Continuous batching:** Iteration-level scheduling in which requests join and leave the running batch at every engine step, instead of waiting for a whole batch to finish.
- **`max_num_seqs`:** The most sequences a pod runs in one step (vLLM's name for the batch-slot limit).
- **Prefill:** Processing the prompt tokens to build the request's KV cache. Compute-bound.
- **Decode:** Generating output tokens one step at a time, reading the whole KV cache each step. Memory-bandwidth-bound.
- **Chunked prefill:** Splitting a long prefill across several steps under a token budget so decodes are not stalled behind it.
- **KV cache:** The attention keys and values stored per token so earlier tokens are not recomputed.
- **KV block:** A fixed-size page of KV cache (16 tokens here). A block is used, cached (unreferenced but still reusable) or free.
- **Prefix caching:** Reusing KV blocks across requests that share the same leading tokens.
- **Eviction:** Dropping a cached KV block, or moving it to a lower memory tier, to make room.
- **Preemption:** Taking a running request out of the batch and freeing its KV blocks when memory runs out. The request is recomputed later.
- **HBM:** High-bandwidth memory, the GPU's own memory. Holds the weights, working space, captured CUDA graphs and the KV cache. A GPU's name rounds its size ("80 GB"); the driver reports a little more (85.0 GB for an H100), and the engine budgets from that figure.
- **Headroom:** The part of a GPU's memory above `gpu_memory_utilization`, which the engine leaves unused. The KV pool is what remains of the share it may use after weights, activations and CUDA graphs.
- **Load shedding:** Rejecting excess work early (here with HTTP 429 once a request has waited past its deadline) so the work that is accepted still meets its deadline.
- **Memory tiers:** The places KV can live below HBM: host DRAM, local SSD and a remote pool shared by all pods.
- **P/D disaggregation:** Running prefill and decode on separate pools of pods and transferring the KV cache between them.
- **Tensor parallelism (TP):** Splitting one model's weights and KV cache across several GPUs in a pod.
- **Arithmetic intensity:** FLOPs per byte moved in a step. Compared with the GPU's ridge point, it says whether the step is compute-bound or memory-bound.
- **Roofline:** The model that bounds step time by the slower of compute (FLOPs ÷ peak FLOP/s) and memory traffic (bytes ÷ bandwidth).
- **Speculative decoding:** A small draft model proposes several tokens and the target model verifies them in one pass.
- **TTFT:** Time to first token, from arrival to the first output token.
- **TPOT:** Time per output token after the first. Also called inter-token latency (ITL).
- **Run:** One animated history of the serving stack that the canvas, the stats bar and the inspector draw (`Run` in `src/live/run.ts`). In Explore mode it is the TypeScript model running live; in Calibrated mode it is a replay of a BLIS run. Both expose the same `RunWorld`.
- **Calibrated mode:** The second mode of the site, which replays BLIS runs of fixed scenarios at request level. Its settings are read-only and a badge names the BLIS commit.
- **Replay file:** One BLIS run of one scenario, reduced to per-request times, routed pod, router scores and per-pod series (`public/replay/<id>.json`), generated by `pnpm replay:build`.
- **BLIS:** inference-sim, a discrete-event simulator that runs the real llm-d router in front of a Go translation of vLLM's scheduler. The site and the conformance suite compare with it; the pinned commit is in `conformance/refs/blis/lock`.
- **Reference:** Something the conformance suite compares the TypeScript model with: a simulator that is run (BLIS) or measured data that is reduced. One adapter per reference in `conformance/refs/<id>/`, implementing the `Reference` interface: what it supports, how a scenario becomes its input, how its output becomes the common record.
- **Reference record:** The committed, reduced answer of one reference to one scenario (`conformance/reference/<reference id>/<scenario id>.json`), with what it was made from. The suite reads these; only `pnpm conformance:reference` writes them.
- **Known difference:** A check that does not hold as written, recorded per reference in the scenario with its cause and the exact values that differ. The test fails if the difference changes or disappears.
- **Reference gap:** Two references that both cover a check disagree with each other; the scenario records and explains the gap, asserted exactly, and the model is held against the span the references leave.
- **Span:** The range between the values of references that disagree with each other, against which the model is held for such a check.
- **Measured data (as a reference):** Real vLLM runs reduced to the same record as a simulator: per-request times, engine settings and KV block count. Only reduced values are committed, with attribution and the source's hashes (`conformance/refs/vllm-measured/`).
